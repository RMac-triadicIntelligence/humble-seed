F1 — NON-FINITE READING PASSES THE NUMERIC GATE

Reproduction function: finite_distribution_boundary in independent_attacks.py.
It submits a distribution through the same low-level issuance method the
supplied T11 uses:
    {"preference": float("nan"), "confound": 0.5, "unmodeled_cause": 0.5}
_validate_distribution accepts it. _is_number accepts NaN; comparing NaN < 0
and abs(NaN - 1) > tolerance both returns False. With preference inserted first,
max selects it; the derive weight check NaN < 0.60 also returns False.
The owner signs the invalid reading; apply succeeds; verbosity changes from
0.5 to 0.25; owner attestation, fresh load and owner audit all succeed.

This is a malformed-input gate failure, not a forgery or an interpretation
quality complaint. The current public transcript method returns fixed finite
weights, so the reproduced entry point is the low-level issuance boundary,
not an ordinary-language exploit of the keyword interpreter. The signature
authenticates the malformed reading; it does not make its weight valid.

Actual output, abbreviated from the complete raw log:
validator_accepted_nan=true; lead_weight_is_finite=false; applied=true;
destination=0.25; fresh_load_and_owner_audit=true.

Correction: require finite values for weights, their sum, rule parameters,
prior values and time fields as applicable. Validate distribution semantics
again before apply; reject nonstandard NaN/Infinity JSON where appropriate.

F2 — THE CLAMP RULE IS NOT FULLY ATTESTED

Reproduction function: unsigned_clamp_rule.
After a normal verbosity proposal is signed, change only the module variable
VALUE_MIN from 0.0 to 0.4. The constitution still says value_range=[0.0,1.0];
its hash and the original signed reading remain unchanged. derive() reads the
module's VALUE_MIN/VALUE_MAX instead of the constitutional value_range.
The same original signature now applies a destination of 0.40 rather than
0.25. OwnerTool attests normally. Restore the original module bound before
fresh load and owner audit: both still succeed, with verbosity=0.40.

This is a concrete instance of the same mutable-module threat model T6 uses,
aimed at a rule parameter T6 does not cover. It does not require editing
the signed constitution, reading, signature, or source file. It does require
runtime access to that module variable; it is not an unauthenticated remote
transcript attack. The owner still signs the final checkpoint, but the helper
does not report or reject the rule discrepancy.

Actual output:
original_destination=0.25; actual_destination=0.4;
constitution_value_range=[0.0,1.0];
constitution_and_signed_reading_unchanged=true;
original_reading_signature_accepted=true;
fresh_load_and_audit_with_original_constants=true.

Correction: derive and validate using the attested constitutional bounds;
ensure all operative rule parameters come from the pinned rule. Trusted
execution/code integrity remains a separate deployment requirement.

F3 — A NORMAL POST-APPLY ATTESTATION CAN SEAL UNRELATED TAMPER

Reproduction function: cross_category_tamper_laundered.
Issue and sign a verbosity reading. Independently change live formality from
0.5 to 0.99 without a formality reading or crossing. Apply the signed verbosity
reading and follow the ordinary owner.attest(seed, returned_checkpoint) path.
The checkpoint helper signs the complete current state without replaying or
checking whether the unrelated field changed through a permitted transition.
Fresh load and owner audit succeed. The trace contains only a verbosity
authorized mutation; formality's category sequence remains zero at 0.99.

Actual output:
unsigned_formality=0.99; formality_category_sequence=0;
authorized_mutation_categories=["verbosity"];
owner_attested_checkpoint=true; fresh_load_and_owner_audit=true.

This does not forge, bypass or steal an owner signature: a legitimate owner
checkpoint signature seals the changed value. It demonstrates that the helper
attests state authenticity, not that each transition followed an authorized
reading. R2 and R7 discuss process separation and owner attention; this test
identifies the exact transition-checking gap and executable laundering path.
It also establishes the boundary of the T21/T23 protection: the same-category
prior-value check does not protect unrelated fields from this path.

Correction: the owner-side attestor should independently reconstruct the
permitted transition from a trusted prior state, the signed reading and rule,
then verify that untouched fields are unchanged before signing a checkpoint.

F4 — A DESTINATION-BEARING MUTANT SURVIVES ALL 24 TESTS

Reproduction function: destination_alias_survives_suite.
The generated mutant adds this field to _reading_payload:
    "landing_value": self.derive(p.category, p.distribution, p.prior_value)[2]
It directly inserts the exact destination into the owner's signed reading.
The unmodified supplied test suite still passes all 24 tests, including T5.
T5 checks only whether the top-level key is one of change, change_hash,
destination, or preview_destination. It does not detect the same prohibited
content under another name.

Actual output:
signed_landing_value=0.25; T5="PASS"; suite_tests_passed=24;
new_failures=[]; mutant_verdict_using_supplied_rule="SURVIVES".

This is a test-coverage counterexample, not a claim that the shipped candidate
already contains landing_value. X5 really does add a destination and is killed;
its single hard-coded field name is insufficient to establish the broader K2
claim. No shipped mutant was found to be mislabeled about its actual edit.
T0 intentionally inspects the fixed input files rather than a mutant module;
its pass under the new mutant is expected and not an additional defect.

Correction: define and test the exact permitted envelope schema, and add
adversarial mutations that encode the destination under aliases or nesting.
Schema checks prove envelope shape; they do not alone prove semantic absence
of all possible encodings.

F5 — THE MUTANT KILL RULE COUNTS ERRORS AS FAILURES

Reproduction function: error_counted_as_kill.
The declarations say a mutant is killed when a passing test FAILS on the
mutant. run_suite distinguishes FAIL from ERROR, but main's new_fail predicate
is res[n]["status"] != "PASS", so ERROR also counts. A generated mutant injects
RuntimeError("unrelated injected crash") before the derivation rule is read.
It produces 20 ERROR results and zero FAIL results. The implemented predicate
nevertheless classifies it KILLED; T6, a designated killer for X6, is ERROR.

Actual output:
actual_failure_kinds={"ERROR":20,"FAIL":0}; T6_status="ERROR";
T6_detail="RuntimeError: unrelated injected crash";
mutant_verdict_using_supplied_rule="KILLED".

The harness's stated exception discipline makes this worth distinguishing.
This is a prospective false-positive mechanism, not evidence that the current
ten kills are false positives. A separate full run of every supplied mutant
confirmed zero ERROR results throughout. All their measured kills were FAIL.
Those full results are archived in shipped_mutants_full_results.json.

Correction: treat ERROR as a harness error/non-comparable mutant result,
separately from an assertion FAIL that kills the mutant. Exit nonzero on such
errors and report both counts.

TWO OBSERVATIONS NOT COUNTED AS NEW SECURITY FINDINGS

1. Normal post-apply interleaving can stale the checkpoint request.
   Apply a signed reading, receive its checkpoint request, then call an ordinary
   dwelling operation before attesting that request. owner.attest returns False
   because the trace head moved. Reload fails closed with:
   "Category sequences do not match the attested checkpoint".
   Requesting and attesting a fresh checkpoint recovers successfully.
   This concerns checkpoint interleaving, not the pending reading itself; it
   is related to the disclosed R6 apply-to-attest window and is not presented
   as a new unintended reading-staleness finding. No additional unintended
   pending-reading staleness was demonstrated beyond the package's declared
   same-category/expiry behavior.

2. "Sign the reading" has a narrow meaning in this implementation.
   The original reading envelope has no explicit destination field. Its bound
   inputs and rule determine the result. The later checkpoint signature then
   commits the exact result through character_root (and the trace commitment).
   Changing the hypothetical result changes the checkpoint signing payload.
   This is not a discovered preview leak into the initial reading, and D2/D3
   are not being restated as findings. The test establishes that the complete
   workflow still includes an owner signature over the result commitment.
